Block 3 · Real time

A live control center on Lakebase

Santa and the elves deliver all over Spain. Every delivery is an event that arrives through Zerobus, goes through Spark Structured Streaming and lands in Lakebase with the Lakebase sink. The app draws it in seconds and an agent reviews the incidents, but only acts when someone confirms.

  1. Today's pain

    Operational dashboards show data that is hours old, and real time means chaining queues, databases and caches.

  2. With Lakebase

    Events into Lakebase in seconds with managed ingestion, or direct writes in milliseconds; the agent decides on fresh data.

  3. The value

    React during the night, not the next morning.

  4. Why it's differentHistory (Delta) and live state (Postgres) on the same platform: no syncing two worlds.
    Measured in the workshopDirect write p50 ≈ 20 ms · Zerobus → Spark → Lakebase p50 12 s / p95 18 s · agent review 7–10 s
    Question for the customer“What decisions would you make if operational data arrived in seconds instead of hours?”
  1. ProducerReplays the night in fast motion: every planned stop is an event. Elves on Christmas Eve, pages on Kings' Night; ~1.5% exceptions.
  2. ZerobusDirect ingestion into a Delta table over gRPC, with no Kafka or Event Hubs. Acknowledges each record once it is durable (at-least-once).
  3. Delta bronzeThe full event history, governed in Unity Catalog: analytics, audit and reprocessing.
  4. Spark Structured StreamingKeeps the latest event per household and per helper, and removes duplicate exceptions.
  5. Lakebase sinkwriteStream.format("postgresql") with upsertkey: INSERT … ON CONFLICT on tables with a primary key.
  6. Control centerThe app reads only what has changed (updated_at cursor): deliveries, positions, exceptions and real latency.
  7. Agent with confirmationQueries Lakebase (household, nearby helpers, similar cases), proposes 2–3 actions from a closed catalog and waits for someone to confirm.

Block 4 · Scale

The primary scales on its own; reads go to a replica

Lakebase's primary compute scales CU up and down with the load, without dropping connections, and shuts down when idle. When the dashboard reads heavily while ingestion writes, you add a read replica: another compute on the same storage, with no data copied. Reads and writes scale separately.

  1. Today's pain

    You size for the peak and pay for it all year; and dashboard reads compete with writes.

  2. With Lakebase

    Autoscaling, scale-to-zero and read replicas in seconds, on the same storage, with no data copied.

  3. The value

    Handle the peak (Christmas Eve!) without redesigning, and pay per use the rest of the year.

  4. Why it's differentScaling or adding a replica is a seconds-long operation, not a capacity project.
    Measured in the workshopRead replica created in 2 s · lag p50 3 ms
    Question for the customer“What is your demand peak, and how many days a year do you pay for it without using it?”
or → / click each step
  1. Primary compute with autoscalingRead-write, between 0.5 and 8 CU depending on load. When idle it shuts down (scale-to-zero: 60 s on this workbench, 300 s on Free Edition) and wakes up on the first connection.
  2. The load arrivesReal-time ingestion (Lakebase sink or direct writes) and the synced tables from Unity Catalog write to the primary.
  3. The primary scalesIt adds CU without dropping connections or changing host; when the load drops, it scales back down. Only compute scales: storage is separate.
  4. The dashboard also reads from the primaryWith everything on one compute, the KPIs, map and exceptions in /control compete with ingestion.
  5. Add a read replicaA READ_ONLY endpoint on the same branch, created in ~2 s: it reads the same pages (no data copied) and has its own autoscaling.
  6. The app reads from the replicaKPIs, map and exceptions, with the badge “Reads: replica”. Measured lag: p50 3 ms · p95 3 ms.
  7. Writes stay on the primarySink, direct writes, the agent and the ▶ / ■ buttons: one table, one writer, always on the primary.
  8. ResultReads and writes scale separately; when there is no load, both computes go to zero.

What a read replica is in Lakebase

AspectRead replica
What it isA READ_ONLY compute endpoint on the same branch as the primary (created in ~2 s)
DataThe same storage as the primary: no data is copied
ComputeIts own, with its own autoscaling and scale-to-zero
LagMilliseconds · measured in the workshop: p50 3 ms · p95 3 ms
ConnectionIts own host; same Postgres roles and OAuth as the primary
WritesNo: INSERT / UPDATE always go to the primary

When to use it

  • Panels and dashboards that refresh often
  • Agents that query a lot (context, searches)
  • Reports and heavy queries during ingestion hours

When not to

  • Reading right after writing (e.g. confirming an action and showing it): use the primary
  • Any write

Block 5 · Branching for agents and what-if

One branch per simulation: DANA in Valencia, closures in Barcelona

The app creates a branch of production in seconds and applies the incident there. pgRouting recalculates the routes and suggests a plan. Production isn't touched until “Apply plan”.

  1. Today's pain

    Testing a change or a “what if” means copying the database (hours, cost, stale data) or touching production.

  2. With Lakebase

    Copy-on-write branches in seconds, with their own compute, that expire on their own.

  3. The value

    Decide with real data and no risk: crisis plans, scenarios and tests.

  4. Why it's differentThe branch is the unit of work: one per simulation, per agent or per developer, thrown away when done.
    Measured in the workshopBranch in 2–3 s · DANA: 1,014 households unreachable and an alternative plan in ≈ 6–8 s · production: 0 changes
    Question for the customer“How do you test a scenario or a migration today without touching production?”

  2. Create branchCopy-on-write from production: ~3 s, with its own compute and expiry.
  3. Apply the incidentRed zone: streets closed or slower (cost of each road segment).

  1. Road network (production)OpenStreetMap → ways edges and vertices. Cost of each edge = length ÷ night speed for its road type (motorway 90, primary 50, residential 25 km/h…). Each household “snaps” to the nearest vertex of the main connected component (household_node).
  2. Scenario → zones, on the branchEach zone is closed, slower (×main roads / ×streets) or lengthens the stop. set_minute activates the zones (Barcelona: by minute) and refresh_costs recalculates the edges they touch: closed = −1 (pgRouting ignores it), otherwise cost × factor.
  3. The night's legsEach route is a sequence of stops (journeys_sync): leg = stop → next. Affected if the line passes within ≤ 300 m of an active zone; unreachable if the destination falls inside a closed zone. At most 3,000 affected legs are routed (deterministic sample).
  4. pgRouting, twicepgr_dijkstraCost with the normal costs and with the incident's. Per leg: no path = no route · > normal × 1.5 + 60 s = detour · > normal × 1.05 = slow · otherwise ok.
  5. Load per routeHow much longer the route takes (travel + stop) over the sample, extrapolated to the affected part: load_factor. If it goes above 1, the last stops no longer fit in the night.
  6. Planner parametersapply_params: each helper (elf or page) adds 60% of one bringer, and the reindeer / camel boost speeds up only the travel (its weight is measured in this simulation). Changing them recalculates on the same branch in ≈ 3 s.
  7. SuggestionsDetours for the 25 worst legs (pgr_dijkstra, with their geometry) · pickup points for unreachable households (clustered with DBSCAN at 800 m) · reinforcement: helpers per route and the last stops for them, children first · reorder ≤ 120 affected stops of the worst route with pgr_TSP.
  8. Decide“Apply plan” copies the suggestions to navidad_geo.applied_plan: the only thing written to production. Or the branch is discarded (≈ 1 s) and no trace remains.

What pgRouting does

A Postgres extension for road graphs: shortest paths, cost matrices, traveling-salesman routes… over an edge table (id, source, target, cost, reverse_cost). Negative cost = an edge that can't be used; reverse_cost = −1 on one-way streets.

FunctionWhat we use it for
pgr_strongComponentsMain connected component of each city: households snap only to well-connected vertices
pgr_dijkstraCostTravel time for each leg in the sample, with the normal network and with the incident (many pairs at once)
pgr_dijkstraThe full path (the edges) of the detours drawn on the map
pgr_dijkstraCostMatrix + pgr_TSPTime matrix between the affected stops of the worst route and their best order (traveling salesman), versus the current order

All with PostGIS alongside (ST_Intersects, distances, ST_ClusterDBSCAN) and in standard SQL: the algorithm runs next to the data, in the database the app already uses.

Formulas 
ratio  = Σ(travel with incident + stop × factor)
         ÷ Σ(normal travel + stop)   · legs in the sample
load   = 1 + (affected legs ÷ route legs) × (ratio − 1)
late   = (stops − unreachable) × (1 − 1 ÷ load)   · if load > 1

parameters (apply_params):
load'  = load × (1 − t + t ÷ boost) ÷ (1 + 0.6 × helpers)
         t = travel share of the night (measured; DANA ≈ 0.62)
suggested reinforcement = ⌈load'⌉ − 1 helpers per route

no scenario (no branch):  load = (1 − 0.62 + 0.62 ÷ boost)

Messages

  • The branch is the lab: it writes zones and costs with its own compute, without touching production, and is discarded in a second.
  • Same data as the app: the routes come from the synced tables, so the simulation and the map tell the same story.

Block 7 · The Grinch attacks (optional)

Human error or Grinch: recover in seconds

On Kings' Night, someone deletes 80 % of the letters and turns the rest into coal. This is operational data: it only lives in Lakebase. Snapshot, branch from a past point in time and recovery, without stopping the app.

  1. Today's pain

    A human error or a script deletes operational data: hours of restore work and the service down.

  2. With Lakebase

    Point-in-time recovery (PITR) and snapshots: branch from the safe moment and roll back without stopping the app.

  3. The value

    Recover in seconds, with no data loss and no downtime.

  4. Why it's differentRecovery is a branch: you inspect it before restoring, instead of restoring blind.
    Measured in the workshopBranch at the safe moment in 2.4 s · 372,830 letters recovered in 5 s · app never stopped
    Question for the customer“How long would it take you today to recover a table deleted by mistake, and what would stop in the meantime?”
  1. Data that only lives in LakebaseLetters to the Three Kings written by the app (they don't come from the lakehouse).
  2. Backup before the nightInstant manual snapshot; better still, an automatic schedule.
  3. The Grinch (or a human error)DELETE of 80 % and UPDATE to coal for the rest.
  4. Investigate without touching productionBranch from the safe moment: copy-on-write of the history.
  5. Recover the damageCopy the rows from the branch back to production in one transaction; the app keeps running.
  6. Plan B: full restoreFrom the snapshot or PITR: new root branch and repoint the app.
ToolWhat you need to know (public docs, check before the session)

Block 8 · Search (optional)

Find families and elves with Lakebase Search

A search bar on every page of the app. BM25 in the same Postgres database that already serves the app: no separate search engine, no copying data out. A family takes you to their home on the map and their visit history; an elf or a page, to the route they covered.

  1. Today's pain

    Search usually means another engine, another index and another sync to keep up to date.

  2. With Lakebase

    BM25, vector and hybrid search inside Postgres, on the read replica too.

  3. The value

    Fewer systems, and results always in step with the data.

  4. Why it's differentSearch lives where the data and its permissions live: one single source of truth.
    Measured in the workshop500,000 families indexed in 25 s · BM25 query ≈ 3 ms
    Question for the customer“How many systems do you touch today so that a search box shows up-to-date data?”
or → / click each step
  1. Enable Lakebase SearchIn the project: Settings → Lakebase Search. Installs lakebase_text (BM25). It's irreversible and restarts the project's computes: do it before the session. Without it, CREATE EXTENSION lakebase_text fails (“must be loaded via shared_preload_libraries”).
  2. Documents from the synced tablesTable navidad_search.doc: 500,000 families (name, city and the names of the people living there) and 364 teams of elves and pages, with the same names as the control center (4 per route). Load: families 26–48 s, teams 11–13 s.
  3. Simple, accent-free analyzerto_tsvector('simple', lower(unaccent(texto))): “García” and “garcia” are the same. No stop-word or synonym tables, so it also works on the replica.
  4. Indexeslakebase_bm25 (3.1 s) computes the corpus statistics when it's built: rebuild it after loading. A GIN index provides the prefixes for search-as-you-type.
  5. QueryBM25 ranks in 2.7 ms on the server; prefixes (GIN, unranked) take ~31 ms — ranking all of them would cost ~146 ms, which is why BM25 does the ranking. The two lists are merged with RRF.
  6. Read on the replicaThe app searches on the read replica (block 4) and writes to the primary. The 'simple' analyzer avoids the stop-word table failure on replicas.
  7. Result on the mapFrom the bar (“/” key) or a suggestion: a family opens “Route map” with their home and history; an elf or a page, their route.

Watch out with replicas

The stop-word or synonym tables of lakebase_tokenizer assign a transaction ID and fail on a read replica. That's why the analyzer is 'simple' with unaccent: BM25 is served from the replica without problems.
